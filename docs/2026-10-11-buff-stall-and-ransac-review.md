# 能量机关卡顿与 RANSAC 对照记录

## 结论

当前症状是识别窗口短暂停住。仅凭平均 CPU 利用率、队列长度不能确定原因；现场尚未取得卡顿帧的分段耗时，因此本次没有宣称卡顿已解决。

RANSAC 有作为大符正弦模型拟合器的价值，但并非大符必须采用的算法。现在这个差分速度、差分加速度预测器在噪声下表现不足，不能仅因计算量小就成为唯一最终模型。最终修改选择 **小符像素卡尔曼 / 大符 RANSAC 正弦模型**；大小符由启动配置选择，每种模式只有一个预测模型。异常或预热只产生无效预测，不切换 FFT、变速器或固定速度。

## 对照的是收藏目录中的这些版本

| 本地实现 | 输入与模型 | 结果如何进入预测 |
| --- | --- | --- |
| 浙大 HWauto_buff2026-main | 连续 roll 的差分速度，RANSAC 拟合速度正弦 | 将 A、Ω、φ、C 送入状态，积分正弦求未来 roll |
| 吉林 jlu_vision_26-master | 角度历史，Ceres + Cauchy 鲁棒损失 | 后台线程拟合，主线程读取参数和拟合时间戳 |
| 常州 Climber_Vision_26-main | 角度观测，包含幅值、频率、相位的正弦 EKF | 从 EKF 状态积分正弦求提前量 |
| 同济 sp_vision_25-main无注释 | 角度观测，正弦 EKF | 同样根据正弦模型积分提前量 |
| 深大 RP-26Rune-main | 连续相位，LM + IRLS 加权拟合 | 拟合 cos、sin、线性时间项及频率，再预测相位 |

这说明应把“运动模型”和“估计参数的方法”分开评估。正弦运动模型可以通过 RANSAC、鲁棒最小二乘、EKF 等方式估计；同时运行多个独立输出模型没有必要。

- [浙大 RANSAC](<D:/rm_能量机关开源/浙大能量机关/HWauto_buff2026-main/src/tracker/ransac_filter.cpp:48>)
- [浙大未来角度积分](<D:/rm_能量机关开源/浙大能量机关/HWauto_buff2026-main/src/predictor/buff_predictor.cpp:33>)
- [吉林后台鲁棒拟合](<D:/rm_能量机关开源/吉林大学能量机关 & 自瞄/jlu_vision_26-master/src/auto_buff/buff_tracker/src/buff_fitter.cpp:36>)
- [常州正弦 EKF](<D:/rm_能量机关开源/常州能量机关/Climber_Vision_26-main/tasks/auto_buff/buff_predict.hpp:139>)

浙大这份代码每次随机选择三个 `(t, v)` 样本，并独立抽取一个候选 Ω。固定 Ω 后，以 `sin(Ωt)、cos(Ωt)、1` 为基求解三个线性参数，恢复 A、φ、C，再按速度残差统计内点。Ω 是速度变化的频率，不是当前扇叶角速度。三点本身不足以同时线性求出所有正弦参数。

其最终提前量是：

`lead = C*h + A/Ω * [cos(φ_now) - cos(φ_now + Ω*h)]`

收藏的浙大实现也有尚未收敛时的线性外推、同步拟合和旧 best_result 保留等行为；本次没有照搬这些行为。吉林将拟合移到后台的做法值得用于耗时超预算的情况，但本次先保持同步、限定计算量并测量实际耗时，避免未经证实就增加线程结构。

## 当前代码发现

1. 改动前 Fu 调用 RANSAC 的 update，但没有使用 predict_roll 生成最终输出。因此它实际没有形成用户描述的有效兜底路径；启用时会额外计算。仓库 YAML 默认关闭 RANSAC，且 buff_move_mode 是 small，微机实际参数仍需现场核对。
2. 大符变速器的输出依赖小符卡尔曼健康，而小符卡尔曼把速度限制在 1.571 rad/s。大符速度可能超过这个上限，两个模型的约束不一致。
3. 旧 FFT 路径包含同步 Ceres，最多 500 次迭代，但触发条件严格依赖样本数。历史最多 300 点，初始化时目标数约为 `2*int(fps*pi)`；约 48 Hz 以上通常达不到目标数。不能直接认定这个优化造成现场卡顿。
4. Fu_Task 在检查是否新帧之前 clone；主循环在没有新帧时仍刷新画面并重复发布失败命令。回调还在 toCvCopy 后额外 clone。相关重复工作已清理。
5. 旧瞬时限频耗时日志可能没有打印真正卡顿的那一帧；其 total 字段也只覆盖部分识别过程，没有覆盖 GUI、回调等完整循环。

## 模拟对照

100 Hz、10 秒，速度 `v(t)=0.9*sin(1.94*t+0.4)+1.19`，前 4 秒用于收敛，后 600 个样本评估。噪声标准差为 0.004 rad，另每 97 帧加入 0.16 rad 的离群观测。双方使用当前亮扇叶锚定和提前量门控。评估的是有输出时的未来角度误差；无输出次数单独统计，不能把零输出解释为零误差。

| 输入 | 提前量时间 | 差分变速器有效输出 | RANSAC 主路径有效输出 | 变速器平均误差 | RANSAC 平均误差 |
| --- | --- | --- | --- | --- | --- |
| 无噪声 | 0.15 s | 600/600 | 600/600 | 0.093° | 0.280° |
| 无噪声 | 0.35 s | 600/600 | 600/600 | 0.953° | 0.730° |
| 噪声 + 离群点 | 0.15 s | 573/600 | 582/600 | 4.424° | 1.260° |
| 噪声 + 离群点 | 0.35 s | 15/600 | 582/600 | 28.615° | 2.874° |
| 噪声 + 离群点 | 0.50 s | 0/600 | 579/600 | 无有效输出 | 4.026° |

这是模型模拟，不是实机命中率或延迟保证。RANSAC 在含噪 0.35 秒场景的 p95 误差仍约 7.98°，说明默认差分速度和阈值还有调参空间，也不能据此宣称 RANSAC 在所有条件下更好。完整数据保存在 [模拟记录](benchmarks/buff_prediction_comparison_2026-10-11.csv)，源代码保存在 `src/rm_tracker/test/buff_prediction_comparison.cpp`。执行 `bash scripts/compare_buff_prediction.sh` 可重新生成 CSV；耗时受机器影响。没有有效输出时误差记为 nan，避免把无输出解释成零误差。

本机这次对照的 RANSAC update 最大耗时约 1.21 ms；旧实现对照曾达到约 3.09 ms。两次运行的调度环境不完全相同，这些数值不能代替微机测量，也不足以认定 RANSAC 是窗口卡顿原因。

## 最终修改

- 大符模型的输出现在真正消费 RANSAC 拟合参数和正弦积分，最终位置仍绑定当前检测到的亮扇叶。
- 实时 Fu 不再包含旧角度差分、FFT/Ceres、固定 60°/s 外推或差分加速度变速器；独立模型源码和测试保留用于离线比较。
- RANSAC 默认 200 次迭代、最多 300 个速度观测、每 5 个新样本拟合一次。三点无放回抽样采用局部交换，求解采用固定 3×3 JacobiSVD，避免每次全窗口洗牌和动态 BDC SVD。
- 丢帧后扇叶别名选择依据已拟合正弦模型的积分，而非只看丢帧前瞬时速度。原已有的 2 秒丢帧回归在旧代码中失败，本次修正后通过。
- 调用层保留大符连续三帧的就绪计数；只在检测异常或已生成的预测点不符合几何约束时重置，不把等待就绪当作异常。
- 同一图像只处理、刷新和发布一次；回调去掉一次冗余 clone，处理前只对新帧 clone。停用显示时主循环在空闲处让出 1 ms。
- 新增完整循环的分段耗时和每秒 p99、最大值；最大值保留同一帧各阶段明细。日志写入自身的长阻塞会作为事件进入下一次统计。

默认模式仍为 `buff_move_mode: small`。打大符时在 `src/rm_tracker/config/rm_fu.yaml` 中设置 `big` 后重新启动。旧 enabled 开关不再选择模型，启动日志会提示已忽略；原有 RANSAC 拟合参数仍可配置。

## 微机下一次卡顿时怎么看

保持原场景先记录 `[BUFF_TIMING]`，再把 `buff_show_image` 改为 false、重启 Fu 做一次相同场景对照。参数在启动时读取，运行中 rosparam set 不会让当前窗口立即关闭。

| 现象 | 后续定位方向 |
| --- | --- |
| worst identify 很大 | OpenVINO 推理、预处理及检测后处理 |
| worst predict 很大 | RANSAC 拟合与实际参数；若超出帧预算，再将单一拟合器移到后台 |
| worst callbacks 很大 | spinOnce 回调批量处理、图像转换或回调日志；串口队列也是候选 |
| worst display 很大，关闭显示后恢复 | imshow / waitKey / GUI 环境 |
| worst output、observe 或 log 很大 | 对应阶段的发布、PnP 或日志 I/O |
| arrival_gap_max 很大，处理各段正常 | 相机、传输、消息调度或前一次循环阻塞，需要与上游发布记录对照 |

capture_gap 是本节点收到的相邻图像时间戳差；队列丢帧也会让它增大，不能单凭该数值证明相机断流。image age 需要相机 header 和 ROS 时间处于同一时间基准。copy 与 callbacks 存在包含关系，不应把所有阶段简单相加。
